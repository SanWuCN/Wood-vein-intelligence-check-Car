# 定位跑偏与"卡住不动"的真正原因：底盘串口驱动退出

日期：2026-09-16。现场现象：巡航中地图与雷达对不上、车容易跑偏，最后卡在原地不动。

## 结论（先看这条）

`runtime/logs/standby.log` 里明确写着：

```
[wheeltec_robot_node]: wheeltec_robot serial port opened
[wheeltec_robot_node] terminate called after throwing an instance of 'serial::SerialException'
  what(): SerialException device reports readiness to read but returned no data (device disconnected?)
[ERROR] [wheeltec_robot_node]: process has died
```

**底盘串口驱动崩了**。它一死，下面这些同时没了：

| 缺失 | 后果 |
| --- | --- |
| `/odom_combined`（实测只剩 0.6 Hz） | EKF 没有轮速可用 → 位姿只能靠雷达硬撑 → **跑偏** |
| `/imu/data_raw` | 姿态与角速度缺失，转弯时更飘 |
| 电池电压 | 界面显示 `—` |
| `cmd_vel` 下发通道 | **车根本收不到速度指令 → 卡在原地不动** |

也就是说"跑偏"和"不动"是同一个故障的两面，**不是地图或参数问题**。核对时底盘状态是
`offline`、电压 `None`、`/odom_combined` 0.6 Hz（正常 10–50 Hz）。重启底盘启动文件后
`/odom_combined` 恢复到 6.5–10 Hz、电压 11.81 V、底盘 `online`。

**现场要检查**：底盘电池电量、串口线/USB 是否松动（`/dev/ttyACM0`）、底盘电源开关。

## 加的守护：底盘自动重启（`chassis_guard`）

以前驱动进程崩了没人管：`start_standby` 只在"没有启动文件在跑"时才启动，而启动文件还活着、
只是节点死了，于是控制台一直以为底盘正常。

现在每 5 s 检查一次底盘在线状态：

- 连续 `down_after_s`=8 s 没有底盘数据 → 判定掉线；
- 冷却 `cooldown_s`=30 s 内只重启一次；
- 按当前模式重启（待命→重起待命；建图→重起建图；巡航→重载当前地图的导航栈），
  并写明确提示："底盘串口无数据（驱动可能已退出），正在自动重启底盘；请同时检查串口线/USB 与底盘供电"。

**实测**：手动 `kill -9` 底盘驱动 → 6 s 后状态变 offline 并给出提示 → 25 s 内自动重启完成，
底盘恢复 online、电压 11.81 V、`/odom_combined` 回到 10 Hz。

## 顺带做的两项调参（都写进控制台生成的运行参数）

**AMCL**（原来是保守默认值，正好放大了上面这个故障）：

| 参数 | 原值 | 现值 | 作用 |
| --- | --- | --- | --- |
| `update_min_d` | 0.25 | **0.10** | 走 10 cm 就更新滤波器，而不是 25 cm |
| `update_min_a` | 0.20 | **0.10** | 转角更新更勤 |
| `max_particles` | 2000 | **3000** | 转弯/遮挡时更稳 |
| `recovery_alpha_slow/fast` | **0.0 / 0.0** | **0.001 / 0.1** | 自恢复原本是关死的：粒子收敛到错位置永远回不来 |
| `max_beams` | 60 | **120** | 似然场用更多光束 |
| `laser_max_range` | 100 | **11.5** | 超过雷达量程的读数按无效丢弃（原来会把"无回波"当有效点） |

**gmapping**（原来 launch 里一个参数都没传，等于全默认）：

| 参数 | 默认 | 现值 | 作用 |
| --- | --- | --- | --- |
| `linearUpdate` | 1.0 | **0.2** | 走 20 cm 就处理一帧扫描（原来 1 m，快走必定畸变） |
| `particles` | 30 | **60** | 建图更稳 |
| `angularUpdate` | 0.5 | **0.2** | 转角处理更勤 |
| `temporalUpdate` | -1 | **0.5** | 静止时也更新 |

现在建图改用显式参数文件起节点（`ros2 run slam_gmapping slam_gmapping --params-file runtime/gmapping.yaml`），
不再依赖厂商 launch 的空参数。

## 补充：那句"底盘里程计或 IMU 无数据"为什么会在一切正常时出现

提示来自启动前的检查 `wait_chassis()`（环境重置、开始建图、加载地图都会走它），它要求
`/odom`、`/imu/data_raw`、底盘原始数据**三路同时在 2 s 内新鲜**。截图那次是串口又瞬时掉了一下：
驱动退出 → 三路同时消失 → 检查等 20 s 就放弃，而文案把原因一概写成"供电和 USB"，
等你回头看时数据早恢复了，所以看起来像误报。

改成：

- 等待时间 20 s → **45 s**；
- 等待期间如果底盘一直没数据（>25 s）且在待命模式，**主动重启一次底盘启动文件**；
- 报错精确列出缺哪路，例如「底盘数据未就绪（缺少：里程计 /odom、IMU /imu/data_raw）」；
- 数据恢复后**自动清掉**之前那条以"底盘"开头的旧报错，不再挂着过期红条。

实测：环境重置 **7.9 s 返回成功**，底盘 online、电压 11.5 V、`last_error` 为空。

## 我改坏又修好的一处：点"开始建图"导致底盘下线

**这是我自己引入的回归**，先记下来避免重犯。

厂商 `slam_gmapping.launch.py` 里其实是三件事的组合：

```python
wheeltec_robot = IncludeLaunchDescription(.../turn_on_wheeltec_robot.launch.py)   # 底盘 + EKF
wheeltec_lidar = IncludeLaunchDescription(.../wheeltec_lidar.launch.py)           # 雷达
Node(package='slam_gmapping', executable='slam_gmapping', ...)                     # 建图（默认参数）
```

我为给 gmapping 加调参，把它换成了只起节点：

```python
args = ['ros2','run','slam_gmapping','slam_gmapping','--ros-args','--params-file',...]   # 只有建图节点
```

而 `switch_mode` 会先停掉待命里的底盘，于是点"开始建图"后：**只有 gmapping 起来，
底盘、EKF、雷达全没了** —— 表现为底盘直接下线、没有里程计/IMU、遥控也发不出指令。

修法：按厂商同样的组合分别起三个作业，既保留调参又不丢底盘/雷达：

| 作业名 | 命令 |
| --- | --- |
| `robot` | `ros2 launch turn_on_wheeltec_robot turn_on_wheeltec_robot.launch.py`（底盘 + EKF） |
| `lidar` | `ros2 launch turn_on_wheeltec_robot wheeltec_lidar.launch.py`（雷达） |
| `slam` | `ros2 run slam_gmapping slam_gmapping --ros-args --params-file runtime/gmapping.yaml`（建图 + 调参） |

`stop_robot()` 同步扩展为停 `standby/robot/lidar/slam` 四个作业。

**实测**：点开始建图 **8.8 s 返回**，`mapping | 底盘 online | 电压 11.81 V | 雷达 9.9 Hz | IMU 有`；
停止建图后 **8 s 内回到待命**，底盘仍 online、11.82 V。

## 连带修掉：底盘守护与"切换模式"抢跑

上一条修好后，加载地图（navigation）又失败了一次：nav2 刚起来就被 SIGINT，
`robot_state_publisher` 抛 `rcl node's context is invalid`。

原因是我新加的 `chassis_guard` 与模式切换抢跑：导航启动时底盘驱动也在重启，
本来就有十几秒没有数据，守护 8 秒就判定"掉线"，于是发起第二次重启
（`safe_stop()` + 再次 `switch_mode`），把正在启动的导航栈杀掉。

三处修正：

1. `switch_mode` 进行中（`self.transition is not None`）守护一律不动；
2. 判定阈值 8 s → **25 s**、冷却 30 s → **60 s**（一次启动本来就要十几到几十秒）；
3. 守护动作放进 `command_lock`，拿到锁后**重新确认**切换状态与底盘状态，避免并发切换。

**实测**：加载 jiaoshi → `navigation | 地图 800x800 | 底盘 online | 电压 11.84 V | 雷达 10.0 Hz | planner True | 定位 True`，无报错。

## "轮子一直在调整"+ 到点后停不下来

用户反馈：车又在点旁停下磨轮子、声音很吵，但定位和地图这次是对齐的（吻合 100%）。
查下来是控制器与容差两个问题：

1. **终点停靠容差被我误设成 8 cm**。上一轮我把"到点判定"和"停靠容差"用了同一个值，
   车到不了 8 cm 内就一直微调 → 轮子持续响。现在两者分开：
   - 行为树**经过半径** = `cruise_arrival_radius`（8 cm，密集航点才分得开）；
   - 终点**停靠容差** = `min(0.25, max(到达半径, 0.20))`（默认 20 cm，停得下来）。
2. **MPPI 缺 `VelocityDeadbandCritic`**：没有速度死区时，控制器会持续输出"一点点前进 + 左右修方向"
   的微指令（就是听到的持续调整声）。现在自动插入该 critic（`deadband_velocity: [0.05, 0, 0.2]`），
   低于死区的速度不会被反复试探。

顺带修掉一个隐形 bug：`/initialpose` 用的是"当前时刻"，AMCL 通过 TF 变换时经常报
`Failed to transform initial pose in time (extrapolation into the future)` 并**丢弃该位姿**——
也就是说静止校准/航行中校准/标签校正发布的位姿其实没生效。现在时间戳回拨 50 ms。

**实机核对**（重新加载地图后）：`goal_checker.xy_goal_tolerance = 0.2`、
`FollowPath.critics` 含 `VelocityDeadbandCritic`、行为树经过半径仍为 `0.08`。

## "点不了预览"的两个原因（都是我引入的）

### 1. 就绪判断依赖了不可靠的动作发现

预览按钮要求 `navigation.planner_ready`，而它来自 `ActionClient.server_is_ready()`。
这台机器上 **ROS 2 动作发现本身不可靠**：新建一个 ActionClient 去探
`/compute_path_through_poses`，`server_is_ready()` 和 `wait_for_server(3)` 都返回 False，
可 `ros2 action list` 里明明有该动作。更糟的是我那次回退分支用了
`Node.get_action_names_and_types()`——rclpy 的 Node 根本没这个方法，异常被吞掉后恒为 False。

改成只用**能观测到的信号**判断导航栈就绪：`巡航模式 + 地图已加载 + scan 新鲜`；
预览不再拿动作发现当初筛，直接发目标，真正失败时再报明确错误。

### 2. 我把不存在的 MPPI critic 写进了配置（更严重）

上一轮为降噪加了 `VelocityDeadbandCritic`，但这台车的 `nav2_mppi_controller` 是 Humble 版，
插件清单里只有 9 个 critic（Constraint / Obstacles / Goal / GoalAngle / PathAlign / PathAngle /
PathFollow / PreferForward / Twirling），**没有** VelocityDeadbandCritic。结果是：

```
[controller_server] Critic loaded : mppi::critics::ObstaclesCritic
[controller_server] [FATAL] Failed to create controller. Exception: According to the loaded plugin descript…
[lifecycle_manager_navigation] Failed to bring up all requested nodes. Aborting bringup.
```

controller_server configure 失败 → lifecycle_manager 中止**整个 Nav2 bringup** →
规划器从未激活 → 预览必然超时。

改成**先读插件清单、有才加**（`available_mppi_critics()` 解析 critics.xml，
读不到就当没有）。降噪改为依赖已经生效的两项：停靠容差 20 cm + 路径跟踪参数。

### 这次的验证（补上上次漏掉的一步）

| 检查 | 结果 |
| --- | --- |
| `ros2 lifecycle get /controller_server` | **active [3]** |
| `ros2 lifecycle get /bt_navigator` / `behavior_server` | **active [3]** |
| 最新一次 bringup 之后是否还有 FATAL | **0** |
| 预览（巡航路线99，10 点） | ok，路径 225 点、到各航点最大偏差 **0.03 m**、最小半径 0.77 m、无过紧转弯 |

## "停在原地 + 跳过好几个点"：起点落在致命栅格

日志给出确凿原因：

```
[planner_server] GridBased: failed to create plan, invalid use: Starting point in lethal space!
[planner_server] Planning algorithm GridBased failed to generate a valid path to (2.86, -1.44)
[behavior_server] Running wait / wait completed successfully     ← 只剩恢复动作
[bt_navigator] Goal failed
```

**车（或它估计的位置）落在代价地图的"内切/致命"栅格里，规划器直接拒绝起步**，
BT 只能反复 wait，最后 Goal failed —— 表现就是"停一会""卡住"。

根因是我之前把"障碍周边 30 cm"做成了**硬禁区**（有效足迹半径 0.30 m = 内切半径）：
只要车离墙 30 cm 内（这张图定位还有偏差），就必然报 lethal space。三项修正：

1. **硬禁区改小、软避让留大**（用户确认的方向）：
   - 硬禁区（足迹内切半径）0.30 → **0.22 m**（`cruise_clearance`）；
   - 软避让膨胀半径保持 **≥0.45 m**，规划器仍会主动挑宽敞通道，但不再"靠近就无解"。
2. **离墙太近先倒车再规划**（`nudge_clear_of_obstacles`）：预览/开始巡航时若起点在冲突区，
   以 0.06 m/s 分小步倒车（每步约 3 cm，最多 42 cm），每步重新判断，让出空间后继续；
   倒车前**必查后方净空**（雷达 ±25°，不足 0.45 m 或无雷达数据就放弃并提示手动挪车）。
3. **行为树加有界倒车恢复**：`BackUp name="BackUpRecovery" backup_dist="0.25" backup_speed="0.05"`，
   与"清代价地图、等待"轮询执行；仍然**不含 Spin**（原地旋转才是之前绕圈的元凶）。

同时**收紧跳点逻辑**（用户反馈"到 6 后直接跳过 7、8、9"）：
- "越过"判据阈值由 5 cm 提到 **10 cm 或半个到点半径**（取大者）；
- 删除"规划要掉头兜圈"这条激进判据（只要路径先朝反方向就跳，正常绕弯也会被误判）；
- "停在点旁到不了"的停滞时间 2.5 → **5 s**、判定半径 0.30 → 0.25 m；
- 两次跳过至少间隔 **3 s**，避免连环跳点。

实机核对：`bt_navigator / controller_server / planner_server / behavior_server` 均 **active [3]**，
行为树里已含 `BackUpRecovery`，全局代价地图足迹半径 **0.22 m**、膨胀 **0.45 m**。
本机 105 项、小车 105 项测试通过。

## 关掉"致命栅格"（贴线巡航）+ 把停车原因显示到前端

用户要求：① 停住的原因要显示在前端；② 关掉避障/致命栅格。

**① 停车原因（`mission.stop_reason`，常驻显示在巡航任务面板）**

规划器/行为树的原始原因控制台看不到（BT 内部调用），因此按可观测信号反推成一句人话：

| 判据 | 显示 |
| --- | --- |
| 起点落在冲突区 | 车离障碍/墙太近（不足 x m），规划器无法从当前位置起步；已尝试倒车让位 |
| 规划结果为空 | 规划器没有找到可行路径：前方被挡、或地图与现场不一致（可考虑“关避障/贴线巡航”）|
| 吻合度 < 45% | 定位吻合度过低（x%），已安全停车 |
| 车没动 | 车没有前进：被障碍挡住，或路径在当前代价地图下不可行 |
| 被取消 / 连续跳点 | 任务被取消 / 航点连续无法到达（最近跳过原因：…）|

**② 致命栅格关掉（贴线巡航）**

硬禁区半径 0.22 → **0.10 m**（≈车体半宽），于是"内切/致命"只存在于障碍本身附近，
规划器不再因为车贴近墙而拒绝起步（`Starting point in lethal space` 消失）；
软避让膨胀收到 **0.20 m**，路径贴教学线走。碰撞风险由用户承担，界面上有明确提示。

- 配置项 `cruise_avoidance`（默认 true）；小车已设 **false**；
- 地图工具栏加了开关按钮（盾牌图标），**运行时通过参数服务直接改两个代价地图**，
  不需要重新加载地图；
- 顺带把起点判定也改用当前生效半径（贴线模式下不再因"离墙 22 cm"报 START_BLOCKED）。

实机核对：全局代价地图足迹半径 **0.10 m**、膨胀 **0.20 m**、`avoidance.enabled=false`、
controller_server / planner_server / bt_navigator 均 active。本机 105 项测试通过。

## "巡航中却停着不动"的真因：控制循环跑不动 20 Hz

用户反馈任务显示"巡航中"但车不动、界面也没有原因。查日志：

```
[controller_server]: Control loop missed its desired rate of 20.0000Hz   ← 连续刷屏
[controller_server]: Passing new path to controller.
```

**控制器根本跟不上 20 Hz**：MPPI 配置是 `time_steps=56` × `batch_size=2000`，
在这台 Jetson（8 核，`load average 7.4/8` 已接近跑满）上单次求解超过 50 ms，
指令断续 → 车几乎不动、还一直微调方向。这同时解释了此前"轮子不停调整"和"走走停停"。

三项修正：

1. **MPPI 减负**（写进控制台生成的运行参数）：`controller_frequency 20 → 10 Hz`、
   `time_steps 56 → 26`、`model_dt 0.05 → 0.1`、`batch_size 2000 → 1000`、
   `visualize/publish_optimal_trajectory=False`。0.1 m/s 的巡航不需要 2.8 s 预测，也不需要 20 Hz。
2. **RViz 改成按需启动**：它常驻要吃掉**整整一个核**。现在只有界面切到 RViz 页才启动、
   切回地图页就关掉（`POST /api/media/rviz {active}`，状态 `rviz_active`）。
   实测负载 **7.40 → 5.31**。
3. **"车没动"要看得见、也要能自救**：
   - 前端在任务运行中实时显示「车已 x 秒没有前进（…）：正在尝试跳过该航点或重新规划」；
   - 后端 `stuck_tick`：连续 `cruise_stuck_s`（默认 8 s）位移不足 3 cm → 取消当前动作、
     跳过该航点继续（`skip_reason='卡住不动，已跳过'`）；累计 `cruise_stuck_max`（默认 6）次仍不行 →
     停车并给出原因（"车连续 N 秒没有前进…多为前方被挡、路径不可行或控制器算不过来"）。

实机核对：`controller_frequency=10`、`time_steps=26`、`batch_size=1000`、
最近日志中 `missed its desired rate` 出现 **0 次**、`rviz_active=False`、两个 Nav2 节点 active。
